# Changelog

All notable changes to Beepboop are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- When the commit signature, a check, the commit status or package metadata stops a release, `beepboop release` asks whether to rerun the failed checks and wait, release without the check, always release without the check, or stop. `--yes` reruns once when a check failed. The card of the stopped release on the runs page shows the same choices as buttons, and `beepboop runs checks ID --choice rerun|skip|always` makes the choice from a script. A rerun reruns the failed jobs of each finished workflow run with a failed check, and the release waits until those runs finish. Release without the check covers the failing and running gates of this release only, and the activity log names who skipped each gate. Always release without the check switches the failed gates off for the stream. Closes https://github.com/kjanat/beepboop/issues/215
- A repository without `.github/beepboop.json` releases when a workflow on its default branch runs `kjanat/beepboop/actions/begin` and setup would change none of its workflows. Beepboop uses the configuration that the setup PR would write, without the binary builds that setup suggests. Other repositories stay unconfigured until their setup PR merges. https://github.com/kjanat/beepboop/issues/215
- `extends` takes the built-in presets `beepboop:default`, `beepboop:npm`, `beepboop:rust-workspace`, `beepboop:github-action` and `beepboop:maintenance`, which load from Beepboop itself without a preset repository. A setup PR that creates `.github/beepboop.json` with a `main` stream writes `"extends": ["beepboop:default"]` and leaves out the values the preset carries, such as `versionScope: one-for-stream`. A setup PR for an existing file keeps every value the file states and adds no `extends`. `beepboop:default` no longer sets `publishWhen`, so a setup that leaves `publishWhen` unticked still reads it as unticked. https://github.com/kjanat/beepboop/issues/215
- The repositories page lists the release gates of each stream: the commit signature, each check on the commit, the commit status and the package metadata, with each gate's state on the commit of the waiting release or the inspected commit. **Switch off** makes every later release of the stream ignore that gate, and **Switch on** undoes it. Beepboop stores the choice on the server, the activity log records who switched each gate, and a release approval names each failing or running gate it ignored. With the package metadata gate off, `actions/publish` publishes a package that lacks metadata. https://github.com/kjanat/beepboop/issues/215
- Beepboop opens a setup PR that rewrites a `.github/beepboop.json` in an older format to the current one. The PR renames deprecated settings such as `versioning` and `approval`, drops the `dashboard` and `cli` entries from `startFrom`, and writes `manager:name` references of discovered packages as package URLs. When the repository allows auto-merge and the PR changes only the format of `.github/beepboop.json`, Beepboop turns on auto-merge with squash, merge or rebase, in that order of preference, and comments on the PR with the result. A closed PR stays closed until the file or the current format changes. A repository without saved setup choices, such as one configured by hand, gets the same PR, and it changes only `.github/beepboop.json`.
- A stream can list `packageTags`, packages that get their own signed tag on the release commit, such as `svg-data-v1.2.3` beside `v1.2.3`. Beepboop creates the tag through the GitHub API once a release published the package. `beepboop tags backfill` creates the missing package tags of earlier releases after a preview and a confirmation. Only packages published at that version get a tag, and existing tags never move.
- A release takes over the version tag that a failed or cancelled release of the same version pushed, when nothing of that version was published. Beepboop moves the tag to the new commit with a lease on the old tag object, and refuses once a registry lists the version, its GitHub release is published or a workflow run of the earlier release or on the tagged commit still runs. A VS Code extension counts as published once the Marketplace or Open VSX lists the version. A version tag that a Go module of the release shares never moves.
- `beepboop runs recover ID --action redispatch` runs the current workflow of the default branch for a failed promotion whose version tag already targets its release commit, and follows the release to its end. A retry re-runs the old workflow, so a fix in the workflow could not release a tagged version.
- `actions/generate-homebrew` and `bun run homebrew` write a Homebrew cask from cask metadata and the release checksums. Each architecture block carries its own `version`, `sha256` and `url`, the URL uses `#{version}`, and a prefixed tag adds a `livecheck` regex. `actions/generate-scoop` and `bun run scoop` write a Scoop manifest with each architecture's URL, executables and hash. See [Homebrew and Scoop](docs/homebrew-scoop.md).
- `kjanat/beepboop/actions/pull-request` commits the changes in a workflow's checkout as the Beepboop App and opens or updates a pull request. It takes `branch`, `title`, `body`, `commit-message`, `base` and `add-paths`, requests the repository token itself and creates a verified commit through the GitHub API. https://github.com/kjanat/beepboop/issues/53
- The runs page has a repository filter, `/runs?repository=<owner>/<name>`, and folds the publications and operations of each release. A release that waits, runs or needs attention starts unfolded.
- `beepboop runs list` shows the current checkout's repository by default and takes `--repository`, `--all`, `--stream`, `--operation`, `--state`, `--releaseVersion` and `--limit`. Its `--json` output is a per-run summary; `--full` prints whole records. https://github.com/kjanat/beepboop/issues/40
- A stream can list `companionModules`, Go modules whose version tag its release pushes on the release commit beside its own tag, such as `go/v1.2.3` beside `rshellcheck-v1.2.3`. The module keeps its own stream. Setup takes the setting as a choices field, the `--companion-module` flag and a JSON editor in the dashboard. Discovery blocks an entry that matches no package and warns about one that is not a Go module versioned by tags.
- `actions/publish` takes `npm-tarballs`, a directory of prebuilt npm tarballs. A generated npm package, such as a platform package from `npm/targets.json`, publishes from the tarball whose `package.json` name and version match, with the tarball's sha512 integrity as its digest.
- When a run fails, the publishing job is its only failed job, and that attempt left every required package that has not published `failed-retryable`, Beepboop re-runs the failed jobs, up to the fourth run attempt.
- Shell completion offers the repository's packages for `beepboop adopt --package` and `--must-publish`, its binaries for `--binary`, and the values of `--start-from` and `--target`. The packages and binaries come from the server's setup plan. Install the completion script again to get them.
- `beepboop release --help` explains what a release does, and which streams only prepare the version.
- `beepboop release VERSION --force` publishes without waiting on commit checks, the commit signature or package metadata, and asks nothing. It restarts a stopped release of that version, and runs its workflow again when the workflow already failed. The `context` output of `actions/begin` carries `force`, so a publication workflow can skip its own tests, and `actions/publish` publishes a package that lacks metadata.
- `beepboop release` shows the binary builds, the publications and the asset uploads of a running release as progress bars side by side. A failed release prints its reason on stderr, piped output included.
- `beepboop` commands that print JSON in a terminal indent and color it themselves. The CLI needs `@kjanat/dreamcli` 5.1.0.
- Adoption notes a Go module whose tags carry the same versions as another stream's tags, or whose tag name a file builds beside that stream's tag name. The note names both options, `companionModules` and moving the module into the stream's `packages`, and changes nothing until you choose.

### Changed

- `beepboop adopt` and the dashboard start every setup field from the same default. For `startFrom`, `versionLands` and `publishWhen`, `beepboop adopt` first offers to leave the question for the setup PR, as the dashboard does. It suggests the only publishing step of a chosen workflow for a single package. The dashboard keeps the job that the proposal names for a generated workflow and the trigger handover saved for the chosen workflow.
- `beepboop release` and `beepboop runs recover --action redispatch` poll a release every 5 seconds for at most 60 minutes, and slow server answers count toward the 60 minutes. Then they stop with exit code 1 and say that the release goes on in Beepboop and that `beepboop runs list` follows it.
- Discovery of a public repository reads its files at the commit from `raw.githubusercontent.com` and spends no installation rate limit on them, and falls back to the GitHub API when that read fails.
- Beepboop reuses a GitHub App installation token for the same repository and permissions until five minutes before it expires, instead of requesting a new one for every GitHub call. Each use still checks the installation's owner, permissions and suspension. A token handed to a workflow run is always new.
- A preset in `extends` loads through Git's ref listing and `raw.githubusercontent.com` without a GitHub API request, so presets stop spending the unauthenticated limit of 60 API requests an hour, and the GitHub API still answers when that read fails.
- Beepboop reads `.github/beepboop.json` with the configuration schema alone, the same schema that `/schema/v1.json` publishes. A file that the schema rejects blocks the repository with the schema's message, such as `prepare` configured under `workflows`, and the `configuration-drift` warning is gone. `prepare.strategy: "workflow"` without `prepare.workflow` stays a warning.
- `beepboop release` and the dashboard start a release on every stream that can start one: they bump the version and publish it, and nothing asks again. A stream that versions each package on its own, a tag-based stream without a promotion that publishes the version tag, and a stream that writes a new version only to version files still only prepare it. `startFrom` only lets the Start release workflow start releases. Setup ignores its `dashboard` and `cli` entries and removes them. Starting a version whose release stopped before its workflow ran restarts that release.
- A release whose required publications are all verified shows `✓` and its version. The badge tooltip carries the count of verified publications, or the note that the stream requires none. A release that waits on its commit shows what it waits for, such as `publish running`, `no verification check yet` or `checks failed: publish`, in the dashboard and the CLI. The dashboard shows the release policy as a tooltip.
- `POST /api/releases/prepare` takes `"start"`. `"start": false` prepares the release, which then follows `promote.publishWhen`, and `beepboop releases prepare` sends it. `beepboop release` and the dashboard send the preview's `"starts"` answer. `"start": true` on a stream that cannot start is refused. `"start": true` for a version that was prepared without a start starts that preparation and rewrites the publication sentence in its open version PR.

### Fixed

- `beepboop release` follows the asset uploads of a release with binary builds. Beepboop reads the draft GitHub release with a token that holds `contents: write`, the push access that GitHub requires for draft releases. The follow stopped with `GitHub HTTP 403 ... Resource not accessible by integration`.
- The setup preview blocks a Go binary build when its main package declares `main.version` as a variable whose type is certainly not `string`, and names the file. The generated build passes `-X main.version`, and the Go linker refuses `-X` for a variable of another type. A type that the source does not resolve, such as one from another package, blocks nothing, and aliases of `string` count as `string`. Files with a build constraint and files that `go build` skips do not count. A `main.version` constant gets a note that names the file: the build succeeds and leaves the version unstamped. Discovery reads the Go sources of each main package to find the declaration. https://github.com/kjanat/beepboop/issues/371
- Setup applies the target limits and the version check of a discovered binary only to a configured build of the same Go package or Cargo manifest. A configured build that shared only its name with another discovered binary took that binary's expected failures and blockers.
- The activity log names the workflow run that read a credential as "Workflow run" with its run number, and a credential read during repository setup as "Beepboop setup". It named both "Administrator".
- A cached installation token that GitHub rejects with HTTP 401 leaves the cache, so the next request mints a new one instead of reusing the rejected token for the rest of its lifetime. A replaced App private key replaces the cached App in the same isolate. A suspension drops the installation's cached tokens, a token without a valid ISO 8601 expiry is never reused, a token is reused for at most 55 minutes, and a token requested by repository name alone is never reused. The owner login and the bot identity refresh every hour, and the installation search reads every page.
- The dashboard's GitHub status panel works on Workers again. Beepboop stored the global `fetch` and called it as a method, and Workers refused each call with "Illegal invocation". Every default `fetch` now goes through a plain wrapper.
- A package watch skips the placeholder version that npm creates for a staged publish, such as `0.0.0-stage`. The watch announced that placeholder as a published version.
- A release whose workflow run succeeds but reports no outcome for a required package checks the registry for it. A package that a run skips because an earlier run already published that version counts as published. A package the registry lacks keeps the release blocked with the reason "The workflow run reported no outcome for" and the package. The release sat blocked without a reason.
- A release skips an unfinished job that has an `environment`, such as an Actions publishing job behind a wait timer in the workflow that verifies the commit. The release waited until that job finished. Such a job that failed still stops the release. A check from a reusable workflow keeps the release waiting when its name can belong to the calling job. A release whose checks are all unfinished jobs with an `environment` or runs of its own release workflows waits with the reason "no verification check yet".
- `beepboop runs publish` clears the reason the release waited for. After a forced publish the CLI printed "Releases when the commit is verified and its checks pass" for a release already on its way.
- A start for a version whose preparation failed or was cancelled restarts that preparation. It keeps an earlier `--force`, and under `concurrency: supersede-pending` it cancels the stream's other pending preparations. The start request answered with success and left the preparation stopped, so the release never published.
- A retry or start of an operation you cancelled clears your cancellation. When GitHub then cancelled the new run, the operation counted as cancelled by you and could not be retried again.
- Adopting a repository with several tag-triggered release workflows gives each tag family its own promotion workflow with that family's tag prefix, and its observed workflow waits for that promotion. Setup gave neither family a promotion. Generated workflow names stay unique across the streams. Unclaimed crates and Go modules join a stream only when the repository has one tag family.
- Setup refuses to adopt a multi-job workflow whose `begin` step has `if` or `continue-on-error`. A `report`, `publish`, `publish-refs` or `publish-release` step or a job whose `if` is the constant `false` covers none of its publications, and neither does a job that needs such a job directly or through other jobs, unless its own `if` calls `always()`, `cancelled()` or `failure()`. Setup counted such steps as coverage.
- Setup refuses a workflow job that runs a `run` step after `begin` or after a checkout and before the checkout of the release source, with or without an earlier checkout. A `report`, `publish`, `publish-refs` or `publish-release` step anywhere before that checkout is refused too. Token, `harden-runner`, setup and other actions may run before it. A multi-job job without a checkout stays valid.
- Merging the version PR or version commit of a tag-based stream that was prepared without a start creates its promotion, which follows `promote.publishWhen`. Beepboop only promoted started preparations of tag-based streams, so the merge published nothing.
- A release of only some packages of a shared-version stream that writes a new version only prepares it, and `start` or `--force` on it is refused. Its merge left the other packages at the old version, and the started release never published.
- Cargo publishing checks and the App manifest request the repository Variables permission as `actions_variables`, the key GitHub uses. An installation with that permission failed every check with `GitHub App installation lacks required permissions (... variables: read ...)`.
- npm publication checks skip invalid `exports` targets when selecting an array fallback and reject an array that ends with an invalid target and has no usable fallback. A valid target still needs its file in the tarball.
- `beepboop release VERSION` for a version that the default branch already carries creates the publication run of the commit that set the version, the same commit a push releases, also after later commits landed. The command fixes that commit when you run it. It failed with `ALREADY_PREPARED` unless `startFrom` listed `cli`.
- A stream with a package that its registry cannot answer for starts no release and shows a `release-unchecked` warning that names the package. The next push or discovery asks the registry again. The warnings of a discovery also stay when a later stream of that discovery fails, and they never replace a newer discovery. The stream started no release and said nothing.
- A version PR that you added commits to before merging publishes on merge with `publishWhen: version-pr-merged`. Beepboop accepts the merged PR while its head still contains the version commit Beepboop opened it with. A started release whose version PR gained commits follows `publishWhen` instead of publishing on merge. The release waited for you to publish it.
- A release stays on the commit that set its version. A later commit on the default branch that leaves the stream's manifests, `versionFiles`, workflow files, the reusable workflows they call and package metadata problems alone creates no second promotion, and the release still waits for the checks of its own commit, publishes, and tags that commit. Publishing it in Beepboop works after the branch moved on. A later commit that changes one of those gets its own promotion as before, and the merge of the version PR or the start of the release does not publish that promotion. A dependent stream waits for the pending promotion of its dependency's version, also when that promotion stays on an earlier commit. The later commit took over the release: it got its own promotion, waited for its own checks, and the version was tagged on it, while publishing the version commit was refused.
- A release on the runs page shows `Publishing` and stays unfolded while a workflow of its stream that lists a required package in `publications` has not finished and that package waits, such as an observed `publish.yml` on the version tag after the tag push. The release showed `succeeded` with its packages waiting.
- Release approval preserves expected refusal diagnostics across Durable Object RPC instead of reporting an internal error. Cargo packages can satisfy license metadata with an SPDX expression or an explicit `license-file`. Registry lookup failures distinguish HTTP errors, timeouts, network failures and unreadable or invalid responses.
- Editing release setup preserves explicitly optional packages. Published optional packages no longer produce a warning that proposes making them required.
- CLI commands accept `--verbose` to show structured API error details on stderr. JSON errors retain the HTTP status and typed problem, including incident IDs, retryability and precondition diagnostics.
- `beepboop runs approve` and `runs publish` accept 7–40 character commit references, including the abbreviated SHA shown by `runs list`. Approval records the full source commit in the audit log.
- A failed or cancelled preparation stops asking for attention once the same version of its stream is released. The release stayed on "Needs attention" after every publication had succeeded.
- A failed release operation ends as succeeded when its GitHub release is published afterwards. On the `release` webhook Beepboop checks that the release is public, that its annotated tag and the other tags of the operation are on the release commit, and records them. The operation stayed failed with the GitHub release `waiting`.
- The publish check on the runs page reads the commit, its check runs, its workflow runs, its status and the tags from GitHub at the same time. It read them one after another.
- Generated binary uploads use `gh release upload --clobber`, so a re-run of a partial publish replaces assets already on the draft instead of failing.
- `actions/publish` goes on to the next package once the registry accepts an upload. The package is `uploaded` until the registry lists it, and Beepboop checks it again while the run hands out packages and after the run ends. A package that depends on it waits for the listing. The action polled the registry after each upload and failed the package when the registry took longer than its polls to list it.
- Tag discovery reads every tag and its commit in one GitHub request per 100 tags. The publish check on the runs page took 18 seconds for a repository with 20 annotated tags.
- `actions/pull-request` refuses the merge commit that a `pull_request` run checks out by default. A pull request built on it held every change of the original pull request. Check out the branch with `ref: ${{ github.head_ref }}`.
- The release form, the repository list, `beepboop release`, `beepboop repositories show` and the release API share one per-stream answer to whether Beepboop starts releases. A stream whose workflows only observe shows what starts a release, such as `release.yml on refs/tags/v*`, and has no Release button. A stream without a publishing workflow says so. Planning or preparing either one is refused with the same sentence. https://github.com/kjanat/beepboop/issues/39
- A stream that reads its version from tags and has no version file or preparation workflow goes straight to a publication run that waits for you to publish it. Preparing it was refused with `A preparation workflow must regenerate lockfiles`. https://github.com/kjanat/beepboop/issues/38
- A release whose lockfiles need regenerating in a stream without a preparation workflow is refused with the stream's name and the missing workflow.
- Run lists read stored `blocked` rows through an index of only those rows. Each list scanned the whole execution history twice to find them.
- An earlier run that still needs you, such as one with an unknown outcome, decides its stage's colour and stays unfolded beside a newer succeeded run.
- The runs page remembers which releases, operations and run details you folded or unfolded when it reloads after a run changes.
- A failed or cancelled run stops asking for attention once a higher version of the same stream has every required publication after it.
- A stage's attempt count leaves out runs that never started.
- The run card links a release only for the operation that creates it, shows `Started on GitHub` as the workflow commit of an observed run, and shortens operation and session IDs in a reason to 12 characters.
- An operation whose workflow run fails after every required publication succeeded ends as succeeded, and its card and stage say that the workflow run failed. An already failed operation changes at the next reconcile, also when a registry shows the publication later.
- The runs page shows each release version as one card: a row of stages (prepare, promote and each extra operation) with a status dot per stage, the attempt count and a link to the workflow run, and one table of every publication of that release. The operations sit below it, opened when they run or need you. Each operation used to be its own card that listed the other operations' packages under "Still to publish".
- PyPI publications link to the project page of the published version, and a GitHub release whose version is a tag such as `rshellcheck-v1.1.0` links to that release.
- Run lists, release summaries and the overview list unfinished runs (pending, ready, dispatching, running, verifying, awaiting approval) before finished ones, newest created first within each group. Cancelling or failing an old run no longer lists it above a newer release, and the 200-run list limit now keeps unfinished runs.
- Retrying a failed observed release whose workflow ref is a tag pattern, such as `refs/tags/rshellcheck-v*`, re-runs the failed jobs of its run. The retry failed with `GitHub HTTP 422 on GET /repos/<owner>/<name>/commits/rshellcheck-v*`.
- `beepboop runs publish`, `cancel` and `recover` accept the 12-character ID that `beepboop runs list` prints, or any unique prefix of 8 characters or more.
- Retrying an observed release whose workflow ref is a shorthand pattern, such as `widget-v*`, checks the tag or the branch the run was observed on. A deleted tag refuses the retry even when a branch has its name, and a tag created later with the name of a branch leaves a branch run retryable.
- Retrying a release whose workflow ref is an exact ref, such as `refs/tags/widget-v1.2.0`, reads that tag or branch itself. A branch with the tag's name no longer stands in for a deleted tag or reports the tag as moved.
- A release pushes the companion module tags that discovery knew when the release was created. A discovery refresh that removes or renames the module during the release no longer drops or renames its tag, and a release whose `companionModules` entry discovery did not find is refused with the module's name.
- Adoption offers `companionModules` only for a stream whose promotion pushes a version tag, and names the prefix that promotion pushes. For a stream that only observes tags it says so.
- A setup rewrite of an already integrated workflow keeps the trailing comments of the steps it does not change, such as `# v5.2.7` after a pinned `uses`, and ends the file with the same final newline as the original.
- Generated release workflows build Cargo binaries with `cargo auditable build`, so the SBOM lists the crates each binary was built with. The SBOM names the repository and release version, gives every file SHA1 and SHA256 digests, and lists no packages or CPEs guessed from asset file names. https://github.com/kjanat/beepboop/pull/72
- A setup rebuild replaces the per-crate `cargo publish --locked --package 'name'` lines an earlier generator wrote with `beepboop publish`, so a rerun skips published crates, retries rate limits and reports each crate. Commands that differ from those lines stay as written.
- A setup rebuild refreshes the commands of every extra operation workflow, not only the preparation and publishing ones. Plain per-crate `cargo publish --locked --package 'name'` lines in such a workflow, for example shellcheck-rs's `publish-crates.yml`, become `beepboop publish` with the crates.io credential.
- A setup rebuild rewrites an already integrated workflow whose publish step runs plain per-crate `cargo publish --locked --package 'name'` lines when the saved command becomes `beepboop publish`. The step becomes the `beepboop publish` action with the crates.io credential, and the report entries for the crates it records are dropped.
- The rewrite carries the publish step's `if`, `env`, `continue-on-error` and `timeout-minutes` onto the `beepboop publish` step, drops only the credential variables, removes the `beepboop_credentials` step only when no other step reads its outputs, and leaves the workflow as written when the step has a setting an action step cannot take, such as `working-directory`.
- The adoption text states each stream's own `publishWhen`, including one a preset supplies, instead of `approved-in-beepboop` for every stream. A stream that pushes a direct version commit is described without a version PR.
- `beepboop adopt` no longer offers workflow jobs that setup cannot patch, such as reusable, matrix, dependent, conditional or container jobs, the job that already publishes, or workflows whose automatic triggers other jobs share. It names why each is left out and asks again, so the choice ends in a generated workflow instead of a blocker at the end.
- A setup rewrite that replaces a step holding a YAML anchor writes the aliased value into each untouched step that used it, also when another step reuses the anchor name. Such a workflow failed to render with `Unresolved alias`, or the untouched step took the other step's value.
- The rewrite to `beepboop publish` keeps the `beepboop_credentials` step when a remaining step or the job's `outputs` reads it in any spelling, such as `steps['beepboop_credentials']`, and leaves the workflow as written when the publish step passes such a credential under a name setup does not manage.
- The rewrite to `beepboop publish` drops report entries only from report steps that carry the begin step's `execution-id` and no `service`. A report for another execution or service stays as written.
- The rewrite to `beepboop publish` keeps a report step it emptied when a later step or the job's `outputs` reads that step's `result`.
